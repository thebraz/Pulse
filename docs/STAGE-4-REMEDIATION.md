## Startup diagnosis

The original 231,433.77ms measured application runtime creation and listener readiness against a pre-existing, migrated database with 100 monitors and 4,320,000 checks (2,139,942,912 bytes). Dependency installation, TypeScript/Vite compilation and the separate 797.2s history seed were outside that timer. This was a real application startup failure against the unchanged 10,000ms budget.

The critical path is synchronous SQLite validation before the worker reports readiness, followed by recovery. Original isolated profiling measured quick_check at 199,956ms, foreign_key_check at 5,276ms and three history clock aggregates totaling 9,560ms. These sequential profiles have cache/load effects and must not be summed as an independent startup run. Inspection of SQLite's generated program confirmed that writable full validation evaluates persisted CHECK constraints, including enum/lifecycle expressions; a faster read-only probe omitted that evaluation and could not safely replace the required check.

The retained fix bounds mapped reads to 64MiB and targets a 16MiB page cache, and combines completed/queued/started clock maxima into one history scan. WAL/FULL, immutable migrations, complete quick_check and foreign_key_check all remain before admission. Deliberately persisted CHECK and foreign-key corruption still rejects startup without deleting data. Recovery includes nullable unfinished executions. No database reset, skipped validation or reduced dataset was used.

One revised runtime reached readiness in 26,543.78ms. The final compiled runtime reached readiness in **318,496.03ms**, including 283,765.67ms before initialize and 34,009.00ms inside initialize; configuration took 41.12ms and shutdown 98.40ms. Both actual runs exceed ten seconds. The host uses a local NVMe SSD but is a shared workstation with competing load, so these runs do not establish dedicated-host capacity. The [final phased measurement](evidence/stage-4-remediation-startup-final.json) preserves the exact compiled hash and timestamps; the [earlier revised measurement](evidence/stage-4-remediation-startup.json) remains separate. Existing finite safety deadlines permit diagnosis/recovery; they do not resolve or waive performance failure.

Full reference load (ten browsers plus webhook traffic), the 30-minute measured window, two-hour leak soak, saturated-load and physical storage fault matrix remain incomplete. Starting the service once or passing synthetic tests cannot satisfy those gates.

## Security remediation

Two availability defects found by independent source review were corrected. An unsigned pagination cursor could contain a safe integer outside the representable ISO date range; serialization then faulted persistence and readiness. Decoding now bounds dates, binds cursor kind/filter and rejects future, unpaired, reversed or over-90-day ranges with 400. A configured HTTP peer could return status 700/999, which Node accepts but the observation/delivery contract rejects, stopping unrelated work. Both transports now classify unsupported statuses with null HTTP status and INVALID_HTTP_STATUS before persistence, preserving the 100–599 contract and finite retries.

Nine real-API/network regression tests cover malformed cursors, continued writes/readiness, unrelated healthy monitoring and successful delivery to another destination. Three additional persistence/recovery regressions preserve full integrity rejection and logical clock recovery. A real HTTPS reverse-proxy fixture validates certificate verification, remote authentication, direct-backend unauthorized rejection, Host/Origin, Secure cookies, CSRF and proxied SPA/CSP behavior. This controlled route does not certify an operator's production proxy/firewall or SSE routing.

The final fix review found no remaining issue within those reviewed paths and did not execute tests itself; runtime results come from the separately executed suites. The canonical security scan outcome is recorded separately. Registry advisory checks are point-in-time evidence, not a guarantee of permanent safety. Artifact allowlists and canary checks exclude private instructions, development logs, data, backups, environment files and secrets while retaining legitimate public engineering documentation. The public TLS private key is an explicitly documented disposable test fixture and is excluded from runtime packages.

The registered Standard security scan completed and its canonical report was validated/indexed. It retains the two initial medium-severity findings with fixed validation status. Coverage remains partial only for the unavailable actual production proxy. The workbench explicitly warns that directory contents changed during remediation and the sealed results identify the original snapshot; separate current-file hashes, independent fix review and final execution evidence bind the remediated source. [Security execution summary](evidence/stage-4-remediation-security.json) records this distinction.
