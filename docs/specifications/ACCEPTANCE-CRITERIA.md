# Pulse acceptance criteria

These are implementation gates, not documentation-completion claims. Rows started NOT TESTED. Stages 1–3 have measured Windows implementation evidence; Stage 4 stable gates retain their recorded statuses. The published experimental beta uses a [separate policy](../guides/BETA.md) and does not change these stable outcomes. Allowed statuses are NOT TESTED, PASS, FAIL and BLOCKED. PASS requires real evidence against the final changed artifact; BLOCKED records a specific missing dependency, never a substitute for an unrun test.

For each executed row, append an evidence record containing criterion ID, revision or candidate SHA-256, command/test name, UTC date, platform/runtime, actual result and report path. Do not place credentials in evidence. A stage exits only when all of its rows and carried-forward regression gates pass. Applicable prior-stage checks must be rerun after material changes.

## Gate rules

Documentation validation checks structure, links, identifiers and contract consistency only. It does not change implementation rows to PASS. Security, recovery and package checks cannot be waived silently. Any accepted exception must identify affected IDs, observed risk, scope and user authorization; it cannot mislabel a failed mandatory criterion as PASS.

Use the stage documents for detailed manual scenarios and [testing strategy](13-TESTING-STRATEGY.md) for fixtures and evidence expectations. Stage advancement and public publication each require explicit authorization even after all technical gates pass.
